# 0018. Scope snapshot: the M2-07 PDF stack, extractable Devanagari, and Cleared's records skip the AI

- Status: accepted
- Date: 2026-11-02
- Ticket: M3-07 (BL-01 6569233018)

## Context

M3-07 turns the agreed scope, the payment, the delivery evidence metadata and the client's acknowledgement into one fixed PDF the seller can attach for PayPal. It is a "scope snapshot", never "signed" (B6 #9). The ticket was written before M2-07 and names `@react-pdf/renderer` with Noto Sans + Noto Sans Devanagari. Since then M2-07 shipped a PDF stack in `packages/adapters/src/pdf/` (pdf-lib, the embedded Hind font, OFL, Latin + Devanagari, fixed metadata, a determinism test). Three more questions came up:

1. pdf-lib shapes custom-font text with fontkit, so Devanagari draws correctly, but the content stream then holds glyphs in visual order (a pre-base matra before its consonant). pdf.js extracts `िडज़ाइन` for `डिज़ाइन`; the ticket asks that Devanagari text extraction round-trips. pdf.js ignores `/ActualText` in text extraction.
2. M3-06 writes a `client_ack` item and emits `evidence.added`, so the M2-03 extract (an AI call) runs on a JSON record, then the scope check (another AI call) re-runs because the evidence set changed. The snapshot item would do the same, and the check would read the snapshot's copy of the scope as more scope evidence (BL-01 6569233018).
3. The job must be idempotent on (pack, input hash).

## Decision

1. **One PDF stack.** The snapshot reuses M2-07's pdf-lib + Hind helpers (`loadEvidenceFont`, `wrapText`, A4, fixed producer/creator and creation date = generated_at). No react-pdf, no second font set, so no `apps/worker/assets/fonts/`. The worker runs TypeScript without a build step and Node cannot load `.tsx`, so the job is `render-scope-snapshot.ts`.
2. **Text that looks and extracts right** (`packages/adapters/src/pdf/glyph-text.ts`). Each line is drawn as the shaped glyph outlines (one form XObject per glyph, GPOS offsets applied), plus the same line as invisible text (render mode 3) in logical order, one glyph per code point, through the whole embedded font's ToUnicode map. This is how OCR'd PDFs work. Search, selection and extraction return the typed text exactly, and the page shows correctly shaped Devanagari. Characters Hind lacks (emoji, CJK) are listed by `missingGlyphs`.
3. **Cleared's records are not AI input.** `client_ack` and `scope_snapshot` (`CLEARED_EVIDENCE_KINDS`) are records Cleared writes from data it already holds. The extract consumer skips them (no AI run). The scope check neither waits for nor reads them, and the pack read model doesn't count them as "still extracting". They still mark a checked pack `stale`, as every new item does (M3-06 AC 6). The same `evidence.added` delivery then calls `settleAfterRecord`: when the newest check's evidence set hash equals the pack's current AI-visible set, the pack goes back to `checked` with no AI run. Otherwise the state stays, and the real item still extracting re-checks the pack when it finishes. An acceptance and the snapshot it triggers cost $0 in AI.
4. **Idempotency by column.** Migration 0014 adds `evidence_items.input_sha256` with a unique index on `(pack_id, input_sha256)`. The input hash is the canonical hash of everything the snapshot prints except `generated_at`. The job takes the workspace lock first (the order `writeEvidence` uses), looks the hash up, and only then renders. A re-run with nothing new returns the existing item.
5. **What is printed.** The newest `scope` item verbatim with its sha256. The payment's capture id, amount, currency, and the date Cleared recorded the payment (PayPal's capture create time is not stored). Items of kind `delivery` and `shipment` as metadata only. The newest `client_ack` whose `scope_sha256` equals that scope item's sha256 (an acknowledgement of an earlier scope is "Not acknowledged by the client"), with accepted_at in UTC and in the workspace time zone, the IP, the user agent and the ack item's sha256. Then generated_at, and on every page the footer "Generated by Cleared from seller-provided text and recorded acknowledgements. This is not a signature or a contract."
6. **Triggers.** The seller's `POST /api/packs/:packId/scope-snapshot` enqueues the command `scope_snapshot.render {workspaceId, packId}`. A `client_ack` item's `evidence.added` runs the same render after the extract step, composed with `inOrder` in that queue's one registry entry.

## Alternatives considered

- `@react-pdf/renderer` + Noto, as the ticket wrote. Rejected: a second PDF engine (and React in the worker) next to M2-07's, a second font set, and a `.tsx` job Node can't load. It still wouldn't fix extraction order, because its fontkit shaping has the same visual-order output.
- Unshaped Devanagari (one glyph per code point, visible). It extracts exactly but draws matras and conjuncts wrongly for a Hindi reader.
- `/ActualText` spans. They're correct PDF, but pdf.js (our extractor, and the one most viewers use) ignores them in text extraction.
- No migration, with idempotency on the output sha256. Rejected: generated_at is printed, so equal inputs at another time give other bytes.
- Keeping the extract on `client_ack` (status quo). Rejected: two AI calls per acceptance that add no facts.

## Consequences

- The snapshot embeds the whole Hind font (~180 KB per PDF), well under PayPal's 10 MB. A 50,000-character scope stays small, because each glyph outline is stored once.
- A pack checked with a `client_ack` before this change carries that item in its stored evidence set hash. Its next check simply runs as for any new evidence.
- M2-07's compiled evidence PDF now typesets pasted text through `glyph-text.ts` too (BL-01 6538667077, fixed in the M3-07 backlog pass), so pasted Hindi chats extract in typed order there as well. It embeds the whole font only when the selection has a text item.
- `SCOPE_KINDS` still lists `scope_snapshot`, but the check never sees one now.
